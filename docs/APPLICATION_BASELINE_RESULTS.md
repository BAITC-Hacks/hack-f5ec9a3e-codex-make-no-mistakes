# Проверка фактического расчёта приложения

23 сентября 2026. Первый эксперимент из [исследовательского плана](REPLENISHMENT_RESEARCH.md) выполнен в отдельном worktree `hackathon-research`.

**Вывод: текущий расчёт действительно совпадает с uncapped weekly EWMA при проверенных настройках. Автоматически заменять его capped EWMA не стоит: меньшая абсолютная ошибка сопровождается большим недопрогнозом во всех четырёх группах. Следующий полезный эксперимент — калибровка буфера на горизонте поставки, а не замена модели по одному WAPE.**

## Что проверено

- Данные прочитаны непосредственно из PostgreSQL в `REPEATABLE READ` с `transaction_read_only=on` и ограничением времени SQL-запроса. Извлечены 238 448 подписанных/пустых/положительных строк за январь 2025 — август 2026. Для прогнозов оставлены положительные расходные накладные; исходные строки сохранены отдельно. Полнота старого периода остаётся предпосылкой бенчмарка, а не выводом из последней даты движения.
- SHA-256 двух исходных книг в PostgreSQL совпали с зарегистрированным экспериментом. Воспроизведены **все 65 754 старые цели**, их количества и прогнозы трёх контрольных правил. Различие написания `Systeme Electric` / `Systeme electric` разрешено по хешу источника, без нечёткого сопоставления товаров.
- Вызваны настоящие `read_inputs` и `calculation.engine.calculate` из application worktree. Для каждого склада, единицы и даты проверено точное совпадение ID исторических строк SQL-читателя с выгрузкой; дубликаты отклоняются. Код приложения предварительно заморожен и не изменился за время прогона.
- Проверены 7, **21** и 28 дней. H=21 соответствует текущему допущению L=14, R=7; остальные горизонты — проверки совместимости. История 56 дней, множители роста/сезонности 1, без исключённых документов, буфер 0 для изолированной оценки прогноза. Политика запасов и качество выбранного пользователем срока поставки здесь не оцениваются.
- Получены 104 499 целей и **417 996 прогнозов** четырёх методов. Максимальная разница функции приложения и независимой weekly-EWMA формулы — `1.400e-11` единицы; контрольных правил и архива — `3.789e-11`.
- Прогон занял **149,1 секунды**, включая SQL, выгрузку, повторные вызовы приложения, расчёт метрик и запись результатов. Это не задержка одного запроса интерфейса. Пиковая память не измерялась.

Периоды прежние: июль–декабрь 2025 — development; январь–август 2026 — уже известное ретроспективное сравнение. Параметры не подбирались заново. Результат не является свежим тестом на будущих данных.

## Главный результат: горизонт 21 день

Одна и та же mature-когорта: первая положительная продажа минимум за 90 дней до даты прогноза. В каждой ячейке **WAPE / bias / недопрогноз**, %. Bias > 0 означает перепрогноз. Недопрогноз — доля недопрогнозированного объёма, а не вероятность дефицита.

| Поставщик / единица | Приложение, uncapped EWMA | Среднее за 28 дней | Capped EWMA |
|---|---:|---:|---:|
| IEK / м | 72,86 / −3,37 / 38,11 | 78,21 / −1,56 / 39,88 | 67,56 / −25,69 / 46,62 |
| IEK / упак | 55,66 / +8,61 / 23,53 | 56,68 / +7,46 / 24,61 | 46,21 / −7,84 / 27,02 |
| IEK / шт | 46,04 / −0,30 / 23,17 | 49,08 / +0,29 / 24,40 | 42,46 / −11,23 / 26,85 |
| Systeme / шт | 49,36 / +11,98 / 18,69 | 47,24 / +5,72 / 20,76 | 44,19 / −17,39 / 30,79 |

Число SKU×дата: 857 / 547 / 14 288 / 4 406 соответственно; это не количество уникальных SKU. Источник: [машиночитаемые метрики H21](application-baseline-metrics.json). Для H21 capped EWMA — заранее фиксированный перенос правила, а не «победитель выбора на H21».

Capping снижает WAPE на 5,30 / 9,45 / 3,58 / 5,17 процентного пункта, но увеличивает недопрогноз на **8,51 / 3,50 / 3,68 / 12,10 п.п.** В каждом из восьми ретроспективных месяцев недопрогноз после capping хуже для каждой группы. Выигрыши WAPE по месяцам: 5/8, 8/8, 8/8 и 5/8. Таким образом, снижение WAPE не означает более безопасную закупку.

В development H21 capping также снижает WAPE во всех группах, одновременно увеличивая недопрогноз. Простое среднее для Systeme немного лучше по WAPE в обоих периодах, но ретроспективное улучшение около 4,30% относительно приложения не проходит предложенный порог 5%, а недопрогноз хуже на 2,07 п.п. Остальные mean28-группы проигрывают приложению по совокупному WAPE. **Ни один проверенный альтернативный метод не проходит одновременно предварительные условия: ≥5% улучшения WAPE и ≤2 п.п. ухудшения недопрогноза.** Это исследовательский фильтр, не согласованный бизнес-критерий; будущий shadow-период ещё не наступил.

Практическая поправка к прежнему исследованию: почти нулевой bias на 28 днях не переносится автоматически на 21 день. На H21 у Systeme bias приложения +11,98%, у IEK/упак +8,61%. Буфер следует проверять отдельно для фактического горизонта и группы, а не одинаково увеличивать всем.

## Редкий спрос, короткая история и пропуски выдачи

Для mature intermittent-сегмента (продажи менее чем в четырёх из восьми последних недель) H21 WAPE приложения: **117,78% / 147,43% / 128,88% / 107,83%**. Недопрогноз соответственно **82,08% / 62,04% / 72,15% / 57,98%**. Хорошее совокупное смещение не означает надёжности медленно продающихся SKU.

В обычном режиме этого эксперимента источники остатков и поставок не передавались. Поэтому отсутствие строки нельзя было считать нулевым прогнозом. Второй вызов с явно синтетическим нулевым остатком принудительно включал товары с прошлой положительной продажей. Их прогноз совпал с обычным вызовом везде, где оба возвращали строку; товары без свежих продаж оставались `needs_review`.

| Mature-когорта H21, 2026 | Всего SKU×дата | Нет строки без синтетического остатка |
|---|---:|---:|
| IEK / м | 857 | 203 |
| IEK / упак | 547 | 159 |
| IEK / шт | 14 288 | 5 489 |
| Systeme / шт | 4 406 | 1 387 |

Это **поведение режима без складских входов**, не оценка пропусков реального интерфейса с выбранными остатками. Синтетический остаток нужен только для одинаковой когорты формул; рассчитанные при нём количества заказа не считаются рекомендациями.

Для товаров с первой наблюдаемой продажей менее 90 дней назад отдельные ретроспективные H21 WAPE: IEK/м 167,60% (15 SKU×дата), IEK/упак 447,12% (14), IEK/шт 195,21% (599), Systeme 56,99% (59). Первые две группы слишком малы для уверенного выбора метода. Это **короткая история продаж, не подтверждённая дата запуска товара**. Товары без единой прошлой положительной продажи и полный каталог холодного старта не оценены. Пропуски и численность сохранены в [проверке покрытия](application-baseline-validation.json).

## Воспроизведение и проверка

Скрипт: [evaluate_application_baseline.py](../scripts/evaluate_application_baseline.py). Он использует существующий Python приложения, его SQL-читатель и калькулятор, а также уже реализованный модуль метрик. Устанавливать зависимости не потребовалось.

Из корня `hackathon-research`, с заранее настроенным `DATABASE_URL`:

```powershell
rtk proxy C:/Users/User/Desktop/hackathon-replenishment/backend/.venv/Scripts/python.exe -B scripts/evaluate_application_baseline.py --app-root C:/Users/User/Desktop/hackathon-replenishment --metrics C:/Users/User/Desktop/hackathon/backend/src/replenishment/metrics/__init__.py --archive C:/Users/User/Desktop/hackathon/experiments/runs/20260923T093731649804Z-baseline-v1 --output artifacts/application-baseline/NEW_RUN
```

Каталог результата должен быть новым. При изменении исходников приложения получится новая версия эксперимента; для точного повторения восстановите замороженный пакет `code/replenishment` в `backend/src/replenishment` отдельного checkout и передайте его как `--app-root`, а замороженный `code/metrics.py` — как `--metrics`. Хеши и версии SQL-источников фиксируются в манифесте, URL подключения не сохраняется.

Успешный запуск: [run-20260923-v2/manifest.json](../artifacts/application-baseline/run-20260923-v2/manifest.json). Рядом находятся `predictions.csv.gz`, `database-movements.csv.gz`, `metrics.json`, `monthly-metrics.json`, `evidence.json` и снимок кода. Они локальные и Git-ignored. Старые зарегистрированные эксперименты не изменены. Незавершённый `v1` не используется как результат.

Проверки завершены:

- Ruff для двух новых Python-файлов — PASS.
- Два синтетических теста — PASS: точная формула, cutoff, чужие склад/единица, отрицательные/нерасходные движения, пустая история, постоянный/нулевой спрос и отдельное правило для 7-дневных упаковок. Тесты не обращаются к БД.
- Независимый потоковый пересчёт WAPE, bias, under/overforecast из сохранённых прогнозов совпал во всех **528 группах метрик**; пять хешей выходных файлов совпали с манифестом.
- Полное совпадение целей и контрольных прогнозов с архивом; независимый просмотр кода не выявил ошибки временной изоляции или сравнения когорт.

## Дальше

Сохранить текущую модель. В следующем эксперименте сравнить семь safety days с калиброванным буфером ошибок именно H21, отдельно по поставщику/единице и активности. Для Systeme и упаковок сначала учитывать перепрогноз среднего; просто увеличить запас по всем SKU было бы необоснованно. Любое улучшение на уже известном 2026 остаётся ретроспективным до будущей проверки.

Фактические fill rate, потери продаж, излишки и экономия **не оценивались**: нет полной исторической картины доступности, остатков, поступлений и резервов. Рабочая модель, данные PostgreSQL и другие worktree не изменены.
