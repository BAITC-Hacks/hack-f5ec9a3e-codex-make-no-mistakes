# Электрокомплект — рабочее место закупщика

## Текущий основной интерфейс

`src/purchasing/main.jsx` запускает `connected-workspace.jsx`: новый дизайн подключён
к API и PostgreSQL. Выбор импортированных SKU → подготовка входов → уточнение
неизвестных данных → серверный расчёт → сохранение версии → утверждение → CSV.
История продаж выбирается отдельно от будущего периода. Корректировки количества
требуют причины; исходные decimal-строки сохраняются без округления JavaScript.
Сценарии доступны после перезагрузки через «Заказы поставщикам».
Ошибки API показываются пользователю, синтетические данные не подставляются.
Учебные сценарии можно выбрать явно. Отправки поставщикам нет.

Запуск: [Docker / локально / F5](../docs/STARTUP.md).
Проверки и ограничения: [DELIVERY_VERIFICATION](../docs/DELIVERY_VERIFICATION.md).

Ниже — описание отдельного прототипа `elektro-workspace.jsx`, который продолжают
менять параллельно. Его локальные утверждение и CSV не являются поведением основного
подключённого интерфейса; сведения о неподключённых данных относятся к прототипу.

Основной frontend открывается по адресу http://127.0.0.1:5173/.
Старая страница /zakupki.html перенаправляет на главную.
Прежние интерфейсы, скрипты и их тесты удалены.

## Запуск

Из frontend/: npm ci, затем npm run dev.
Проверка: npm test и npm run build.

## Рабочий процесс

Выбрать склад и категорию → задать период → рассчитать → проверить обоснования
и количества → утвердить → скачать CSV. Корректировка требует причины.
Изменение входов или количества отменяет утверждение.

Период прогноза задаётся собственными начальной и конечной датами, без фиксированных
пресетов. Обе границы включены. Изменение любой даты пересчитывает число дней;
ввод количества дней изменяет конечную дату; допустимость проверяется по API. Начальное значение — 21 день.
История продаж имеет отдельные границы в настройках расчёта;
доступная синтетическая история: 23.09.2025–22.09.2026.

## Расчёт через API

POST /api/v1/planning/calculate — единственный источник прогнозов, рекомендованных
количеств и объяснений. Browser не рассчитывает прогноз и не подменяет ошибку API
локальным результатом. Backend должен быть запущен; Vite использует существующий proxy.
Запрос передаёт явную конечную дату `forecast_end` и `forecast_method: auto`.
Горизонт от 1 до 730 дней одинаков для всех товаров; срок поставки не прибавляется
повторно. Обе даты в UI включены, coverage_end API — исключающая граница.
Метод: weekly EWMA по последним 56 дням или среднее при короткой истории / включённой
компенсации stockout. Явный дневной спрос товара сохраняет приоритет.
Подробности: [контракт периода](../docs/CUSTOM_FORECAST_PERIOD.md).

Файлы fixtures генерируют только синтетические продажи, остатки и поставки для 8 SKU.
При изменении алгоритма на сервере контракт запроса/ответа сохраняется.
График использует daily_balances[].demand; исключения, потери и предупреждения —
соответствующие поля ответа. Сравнения очистки/stockout выполняют два API-запроса.
Дневной очищенный ряд не возвращается текущим API и не рисуется как фактический.

Обоснование SKU содержит график, входные крупные продажи с анонимным ID,
периоды отсутствия, API-сравнения и решения по каждому ожидаемому поступлению.
Источники показывают покрытие текущего сценария отдельно от импортированных книг.
Импортированные данные пока не питают демо. BOM отсутствует.

Утверждение и CSV в этой версии остаются локальными frontend-действиями;
сохранение сценариев через API не подключено. CSV содержит обоснования сервера.
Автоматическая отправка отсутствует. Состояние теряется при перезагрузке.
